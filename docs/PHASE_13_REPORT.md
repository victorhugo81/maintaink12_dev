was no real data to lose or migrate.

## A real, hard-earned lesson from this session, not specific to this phase

While preparing this phase's own migration, a prior migration (Phase 12's Site
city/state/zip/principal-contact columns) was discovered to still be **unapplied on the
user's live MySQL database**, causing a `(1054, "Unknown column 'site.site_city'")` 500 on
every page touching `Site` — including the root dashboard. That migration had only ever been
verified against a disposable local SQLite file (correctly — a scare earlier in the session,
documented in the session transcript, established that `.env`'s `DATABASE_URL` now points at
a real district database, and no migration workflow command should touch it without an
explicit, separate `flask db upgrade` step run with the user's confirmation). Root cause:
verifying a migration locally and *applying it to production* are two different steps, and
skipping the second silently breaks the live app the moment code depends on the new column.
Fixed by running `flask db upgrade` against the live DB (confirmed via `flask db current`
that it was exactly one revision behind, then applied — additive-only, 12 existing site rows
confirmed intact afterward). Documented here because it's a hard rule for any future schema
change in this project: **verify locally, then explicitly apply to whatever the live `.env`
points at, as its own visible step — never assume verification implies deployment.**

## A second real bug, caught the same way

Retrying against the live database (after the migration verified clean on SQLite) hit a
genuine MySQL-only failure: `(3730, "Cannot drop table 'title' referenced by a foreign key
constraint 'ticket_ibfk_1' on table 'ticket'.")`. The autogenerated `upgrade()` dropped
`title` before `ticket`, which still had a live FK pointing at it — MySQL enforces this at
DDL time; the disposable SQLite scratch baseline used for verification had declared the
tables with plain columns, no FK constraints, so it never exercised drop order at all. Fixed
by reordering to children-before-parents (`ticket_content`, `ticket_attachment`, `ticket`,
`title`), then re-verified against a *second* SQLite scratch baseline — this time with real
`REFERENCES` constraints and `PRAGMA foreign_keys=ON` — before retrying live. Confirmed
before and after that nothing had actually dropped from the failed first attempt (MySQL's
per-statement implicit commit meant the very first statement failing left every table
untouched). The corrected migration then applied cleanly to the live database: all four
tables gone, 43 tables remaining (was 47), 12 `site` rows confirmed intact. Lesson for
`application/CLAUDE.md`: a scratch-baseline verification that doesn't declare real FK
constraints can pass while the live schema's actual constraints still reject the same DDL —
build the baseline with the real constraints when a migration drops or reorders tables with
foreign keys between them, not just when it adds a new one.

## Deviations / judgment calls

1. **`/dashboard` kept as a redirect rather than removed outright** — no instruction either
   way; kept for backward compatibility with anything that bookmarked or linked the old URL,
   at near-zero cost (three lines).
2. **The `ticket-content-box` CSS class name was left as-is** across every M&O detail
   template (`edit_facility.html`, `edit_work_order.html`, etc.) despite its ticket-era
   origin — renaming it touches every detail template for zero behavioral change; noted in
   `application/CLAUDE.md` so a future reader isn't confused by the name.
3. **The downgrade path for migration `13e58200527c`** recreates the four tables from
   Alembic's autogenerated diff, which doesn't reconstruct the original foreign-key
   constraints (the disposable scratch baseline used for verification declared plain columns,
   not FKs, to keep the baseline-building script simple) — acceptable since a downgrade here
   is an emergency escape hatch for getting columns back, not a real rollback with data.
4. **Not part of the original 12-phase plan** — this phase exists because the user asked for
   it mid-session after Phase 12 was already complete; numbered 13 to keep the
   `docs/PHASE_N_REPORT.md` convention consistent with every prior phase.
