What This App Is
Maintaink12 is a lightweight CMMS / work-order management system for K-12 district Maintenance & Operations (M&O) departments, built directly on top of the AssistItK12 codebase (a K-12 IT ticketing platform: users, roles, sites, tickets, assignments, attachments, notifications, reporting). See docs/PROJECT_PLAN.md for the full target vision, data model, KPI list, and phased build-out — read it before extending this app. Maintaink12 and AssistItK12 are separate projects (no shared git history); this repo started as a copy of AssistItK12's application code and diverges from here via the phases in docs/MAINTAINK12_PLAN_AND_PROMPTS.md.

As of Phase 12 (the final phase), the app still contains the AssistItK12 ticketing system untouched, plus the M&O modules added so far: Facility/Floor/Room (Phase 1), AssetType/Asset/AssetConditionHistory with QR codes (Phase 2), WorkOrder with Priority/Category/Subcategory and a status workflow (Phase 3), MaintenancePlan/MaintenanceSchedule with automatic PM work-order generation (Phase 4), InspectionTemplate/Inspection/InspectionResult with due/overdue tracking and failed-item work-order generation (Phase 5), Vendor with a WorkOrder.vendor_id link and a performance view (Phase 6), WorkOrderLabor/WorkOrderMaterial/CostRecord with cost rollups and technician workload (Phase 7), Project/ProjectTask/ProjectCost/ProjectDocument with Asset Risk Scoring and Capital Replacement (Phase 8), the role-based M&O Dashboard at /dashboard with Facility Health Scores, Recurring Issue Detection and Operational Insights (Phase 9 — no new models, one new index), thirteen CSV-exportable Reports at /reports (Phase 10 — no new models, no new migration, pure reuse of existing modules), and SLARule/NotificationPreference/NotificationLog/CsvImportLog powering configurable SLA targets + breach/warning tracking, an 8-category email notification sweep, global search, and a generalized CSV import tool for Facilities/Rooms/Assets/Vendors/Users (Phase 11), and Running the App
# Run dev server
uv run flask --app main.py run

# Or activate the venv and use flask directly
source .venv/bin/activate
flask --app main.py run
Dependencies are managed with uv. To add or sync packages:

uv sync
uv add <package>
Database
MySQL via PyMySQL in production; SQLite (DATABASE_URL=sqlite:///...) works fine for local dev — set FLASK_CONFIG=development in .env either way. Connection string is in .env as DATABASE_URL.

# Apply all pending migrations
flask --app main.py db upgrade

# Generate a new migration after model changes
flask --app main.py db migrate -m "description"

# Check current migration version
flask --app main.py db current
Migration files live in migrations/versions/. After adding or changing a model, always run migrate then upgrade. IMPORTANT: the migration chain's root revision (b47d77fd2576) is not runnable against a truly empty database — it assumes the baseline AssistItK12 tables already exist (created via db.create_all(), the way installation/seed_data.py bootstraps a fresh install). To test a migration against a "pre-existing production" baseline instead, create all tables except the ones your migration adds (db.metadata.create_all(bind=db.engine, tables=[...])), `flask db stamp <previous head>`, then `flask db migrate` / `db upgrade` — that's how the Facility/Floor/Room migration (7d40fabd6b8b) was verified additive.

Adding a column to an EXISTING table (not just creating new tables) needs a stricter baseline than the "skip the new tables" trick above — that trick only works when nothing about existing tables changes. Phase 6's `WorkOrder.vendor_id` needed the real work_order table minus exactly that one column; the reliable way to build that is to compile the table's real CREATE TABLE DDL (`str(CreateTable(table).compile(engine))`), strip just the target column's line (regex-fix the resulting trailing comma), execute that DDL directly, then `create_all()` every other table normally. Naively rebuilding the table from `Column.copy()`-filtered columns loses constraint fidelity (names, etc.) and produces false "everything changed" autogenerate diffs — a case of the surgery itself, not the real migration, being broken. Don't trust a `Column.copy()`-based baseline for this class of change.

flask-migrate's `render_as_batch` default means autogenerate ALWAYS wraps an ALTER in `op.batch_alter_table(...)`, on every backend, not just SQLite. That's normally harmless — MySQL executes the enclosed operations as plain ALTERs when it can. But adding a NEW FOREIGN KEY CONSTRAINT to an EXISTING SQLite table forces batch mode into its "recreate the whole table" strategy, which requires every one of the table's pre-existing constraints to be reflectable with a name — and none of this project's FKs have explicit names (plain `db.ForeignKey(...)` on a Column, no `name=`). That combination fails with `ValueError: Constraint must have a name` on SQLite; MySQL has no such limitation (a plain `ADD COLUMN ... ADD CONSTRAINT` needs no recreate there). The Phase 6 migration (`a370d33e0db2`) works around this by checking `op.get_bind().dialect.name` and only adding the DB-level FK constraint on non-SQLite backends — SQLite gets the column and the ORM-level relationship, just not a database-enforced constraint on that one column. Keep this pattern in mind for any future migration that adds a FK-referencing column to a table that already has other unnamed FKs on it.

Seeding Data
# 1. Create MySQL DB and write .env (interactive)
python installation/create_env.py

# 2. Seed roles, default site, admin user, ticket titles (interactive)

seed_data.py calls db.create_all() itself, so it's also the fresh-install path for local SQLite dev — no need to run `flask db upgrade` first. Architecture
App Factory
main.py contains create_app(config_name). It initializes Flask extensions (SQLAlchemy, Flask-Login, CSRF, Flask-Mail, Flask-Limiter, APScheduler), registers the single blueprint, applies security headers, and wires database-stored SMTP config from the Organization model. It also creates the upload folders: UPLOAD_ATTACHMENT (tickets), UPLOAD_FACILITY_ATTACHMENT, and UPLOAD_ROOM_ATTACHMENT.

Single Blueprint
All routes live in application/routes.py under one blueprint (routes_blueprint), organized into labeled sections:

Auth — login, logout, set-password, account lockout
Users / Roles / Sites / Notifications / Organization — admin management
Tickets — list (filtered/paginated), add, edit/detail (comments + attachments), delete, titles
Facilities / Rooms (M&O) — see below

Facilities / Rooms (M&O) access model
GET (list/detail) is open to any @login_required user, scoped by can_access_site() in routes.py — Admins/Specialists (role_id 1/2) see every site, everyone else only their own, mirroring can_access_ticket()'s pattern. POST (create/edit/delete/floor management/attachment upload+delete) is gated by is_admin(), matching how Site management already works — there's no partial "M&O role" permission model yet, since PROJECT_PLAN.md's expanded role list (M&O Director, Supervisor, Technician, etc.) hasn't been built. edit_facility.html/edit_room.html/edit_asset.html render the same page for both cases, just with form fields marked readonly/disabled and the management controls hidden for non-admins — the real enforcement is server-side in the POST handlers, not the disabled attribute. One exception: add_asset_condition (recording a condition assessment) is open to role_id 1-3 (Admin/Specialist/Technician), site-scoped, because technicians are the ones inspecting equipment. AssetType CRUD (list included) is admin-only like Sites/Titles.

Work order access (can_access_work_order / can_manage_work_order in routes.py) mirrors tickets exactly: Admin/Specialist (1/2) see and manage everything; Technicians (3) see and manage their own site's; everyone else sees only work orders they requested or are assigned to, and may comment but not edit or change status. "Staff" (is_staff(), roles 1-3) can create Manual work orders via /add_work_order; anyone can submit a Request via /request_work_order, limited to facilities at their own site. Assigning a technician to a New work order auto-moves it to Assigned (the only place a status changes outside the status-change route, and it still goes through apply_transition).

Detail pages with a secondary action (add floor, record condition, change status, add comment, add subcategory) put that secondary <form> OUTSIDE the main edit <form> — HTML doesn't allow nested forms, and a browser silently folds the inner form's fields into the outer one, so the secondary submit button posts the wrong form. This bit edit_facility.html once; curl-based smoke tests don't catch it, a nested-form depth check on rendered HTML does.

QR codes: /asset_qr/<id>.png renders on the fly with the `qrcode` library (no stored image) and encodes asset_qr_url(asset) = the edit_asset detail URL built with _external=True — so it depends on the request host/scheme (behind a proxy, ProxyFix in main.py is what makes that right). Login is still required to open the page a QR resolves to.

Key Conventions
Soft delete for M&O structural data: Facility.is_active / Room.is_active, not a DB row delete — see the Models table above. Existing AssistItK12 entities (Site, Role, Title, Notification) still hard-delete.
WTForms BooleanField + hidden checkboxes: a checkbox field only appears in POST data when checked — omitting it (e.g. in a test, or a customized form) silently sets the field False. FacilityForm.is_active / RoomForm.is_active rely on this being resent correctly by the real template; add_facility.html/add_room.html never render the field at all, so new records keep the column default (Active) instead of risking this footgun. The ticket form works around the same footgun differently for `escalate` (routes.py checks `'escalate' in request.form` explicitly) — that alternate pattern is only needed when the field is conditionally hidden for some roles who can still POST the form, which isn't the case for is_active.

Frontend Visual Design System
The UI was redesigned from a gradient-heavy "admin template" look to a flat, bordered, editorial style. Everything lives in application/static/css/style.css as CSS custom properties — there is no build step or preprocessor.

Design tokens (:root in style.css)
color-primary (#153448, fixed brand navy), color-secondary (slate), color-accent (terracotta, used sparingly for CTAs/active states), plus color-success/-warning/-danger/-info and neutral color-bg/-surface/-border/-border-strong/-text/-text-muted. Bootstrap's own bs-primary, bs-success, bs-warning, etc. are re-pointed at these so stock bg-success, badge, alert, and form-validation colors stay in sync without touching template markup.
radius scale is restrained (radius-sm 5px to radius-xl 14px) — avoid introducing new pill-shaped elements outside badges/switches.
shadow is used only for overlays (dropdowns, modals, the login card); flat surfaces get a 1px border instead of a shadow.
Inter is the only typeface, with a real weight/size hierarchy defined near the top of the file (space scale, h1 to h6 rules).

Component conventions
Buttons (.btn and variants) always carry a visible border in a matching darker shade — never a borderless flat fill — per the accessibility pass.
Page headers: templates still use the original markup classes (.custom-title-card, or .bg-gradient-main.shadow-dark.border-radius-lg on add/edit forms) — these are intentionally not gradient banners anymore. They are flattened entirely in CSS via compound selectors so the 20+ CRUD templates didn't need markup changes. If you add a new list/form page, reuse the same class pair rather than inventing a new header style.
Cards and tables are bordered, not shadowed; table headers use a light sunken background, not a solid dark fill.
Focus states use a global :focus-visible outline in the accent color — don't suppress it with outline: none on new interactive elements.

Navigation (application/templates/includes/nav.html)
The sidebar is a flush, full-height, dark-navy panel, not a floating white card. Active links get a left accent border, not a filled pill — set via a plain active class in the Jinja conditional, not bg-gradient-main text-white. The top bar's navbar-collapse has no real Bootstrap toggler anywhere in the markup, so ".navbar-main .navbar-collapse { display: flex !important }" in style.css keeps the mobile hamburger and user info visible at every breakpoint — don't remove that rule or mobile nav disappears.

Backend Security Architecture
These patterns came out of a full security audit and its fixes — preserve them when touching nearby code.

Config resolution: create_app(config_name=None) in main.py resolves config_name from the FLASK_CONFIG env var, falling back to 'default', which maps to ProductionConfig in config.py. Local development must set FLASK_CONFIG=development in .env (DevelopmentConfig is the only place SESSION_COOKIE_SECURE is turned off, for plain-HTTP testing). The production startup guards in create_app compare the resolved class (config[config_name] is ProductionConfig), not the string 'production' — so they still fire when config_name resolves to 'default'. Don't reintroduce a string comparison there.

Ticket authorization: can_access_ticket(ticket) in application/routes.py is the single authorization check for ticket detail/comment/attachment routes (edit_ticket, add_comment, download_attachment, delete_attachment). Admins/Specialists (role_id 1/2) can access any ticket; Technicians (role_id 3) are scoped to their own site, matching the /tickets list filter; everyone else only their own tickets. Any new ticket-detail-style route must call this helper rather than re-deriving its own role_id check — the routes previously each had a slightly different inline check, and Technicians could reach other sites' tickets by guessing a ticket_id.

Facility/Room authorization: can_access_site(site_id) in application/routes.py is the read-access counterpart to can_access_ticket() for the M&O module (edit_facility, edit_room, download_facility_attachment, download_room_attachment) — Admins/Specialists (1/2) see any site, everyone else only their own. It only guards GET; every mutating Facility/Room route also calls is_admin() explicitly.

edit_user authorization: non-admin "tech role" staff (Specialist/Technician) may only edit non-admin users at their own site. role_id and site_id choices are restricted server-side, not just in the rendered <select> — see the re-validation inside form.validate_on_submit(). Don't loosen this without equivalent re-validation; the original version let any tech-role account promote itself (or anyone) to Admin and reset any user's password.

delete_user blocks deleting your own currently-logged-in account and deleting the last remaining Admin (role_id=1).

Login (routes.py:login) always runs a password-hash comparison — even for a nonexistent account, via the module-level _DUMMY_PASSWORD_HASH — and always shows one generic failure message regardless of whether the account doesn't exist, has the wrong password, is inactive, or is locked. This is intentional (anti-enumeration); don't reintroduce per-case messages.

CSP: main.py issues a fresh nonce per request (g.csp_nonce) and script-src only allows 'self' plus that nonce — there is no 'unsafe-inline' for scripts. Any new inline <script> block in a template must add nonce="{{ g.csp_nonce }}" or the browser will silently block it.

Rate limiting: the Limiter in main.py has global default_limits (200/hour, 50/minute per IP), with the static endpoint explicitly exempted via a request_filter (otherwise normal page loads 429 on their own CSS/JS). Login (5/min), set_password and test_email (10/min), and add_comment (20/min) carry their own tighter @limiter.limit(...).

Dependencies: pip-audit is a dev dependency (uv run pip-audit) — run it before any release. It has already caught real, then-current CVEs in cryptography and idna once.

Preventive maintenance generation (application/pm.py): generate_due_work_orders(today=None, user=None) is the one place PM work orders get created — called by the daily APScheduler job (scheduled_jobs.run_pm_schedule_generation, registered unconditionally in main.py's create_app, 1am cron) AND directly by the admin "Run PM Generation Now" button (routes.run_pm_generation) AND by tests. Never duplicate this logic elsewhere. Duplicate-prevention works by advancing MaintenanceSchedule.next_due_date past `today` in the SAME transaction that creates the work order — there is no separate "already ran today" flag, the advanced date IS the guard. An overdue schedule (job didn't run for a while) still gets exactly ONE work order per call, with next_due_date fast-forwarded cycle-by-cycle past today — it does not backfill one work order per missed cycle. Schedules for a type-based plan are created lazily (_ensure_schedules), one per matching active asset, the first time generation runs after the plan/asset combination exists — so adding a new asset of a monitored type, or activating a new plan, doesn't need any migration or manual step to pick it up.

Cost rollups and technician workload (application/costs.py): `cost_rollup(work_orders, dimension)` groups a list of already-loaded WorkOrder objects in Python (not SQL `GROUP BY`) — fine at this project's current scale, matching the same N+1-adjacent tradeoff already flagged for the ticket dashboard in `PHASE_0_ARCHITECTURE_ANALYSIS.md` §8 and the vendor performance view in the Phase 6 report; revisit alongside Phase 9 if work order volume grows large. "Department" as a rollup dimension has no backing model anywhere in this schema (PROJECT_PLAN.md names it without ever defining one) — mapped to `WorkOrder.assigned_team`, falling back to the assignee's name, then "Unassigned". `technician_workload()` scopes to `role_id == 3` (Technician) specifically, matching the plan's literal wording, not Specialists too.

M&O Dashboard (application/analytics.py, route `mo_dashboard` at /dashboard — the legacy ticket dashboard at "/" is untouched): the ONE place PROJECT_PLAN.md's Canonical KPIs are computed; Phase 10's reports should call these functions, not re-derive KPIs. Unlike costs.py/vendors.py/risk.py, this module aggregates in SQL (`GROUP BY` / `SUM(CASE ...)` over the indexed work_order columns) rather than loading rows into Python — the plan's performance baseline — with exactly one row-level scan (recurring-issue detection, capped at `RECURRING_SCAN_LIMIT` newest rows of a few plain columns) and every template list `LIMIT`ed. Two contracts to keep: (1) every widget takes the same filter dict from `parse_filters()` and applies it through `_wo_clauses()`, so a filter can never apply to one chart and not another; "point-in-time" KPIs (Total Open, Overdue, PM Due...) ignore the date range on purpose, "in period" ones (Opened, Completed, cost, charts) use it. (2) `facility_health()` follows `risk.calculate_risk()`'s rule exactly: a factor with no data is EXCLUDED from the mean, never counted as 0 — only Open/Overdue and Recurring Problems are always available. Date math is dialect-specific in SQL (`_days_between()` branches on `db.engine.dialect.name`: julianday on SQLite, TIMESTAMPDIFF on MySQL) and month grouping uses `extract()`, which SQLAlchemy compiles per dialect — don't replace either with `strftime`/`DATE_FORMAT`, which only work on one backend. Where the plan names a KPI without defining it (Backlog, Completion Rate, SLA Compliance %, Repeat Work %, Assets Requiring Attention) the definition lives in that function's docstring — SLA Compliance is due-date based until Phase 11's SLA model exists. Role views: Admin/Specialist may switch Executive↔M&O Manager; Technician and School Staff views pin the filters to the user (`assigned_to`/`requester`) and their site inside `build_dashboard()`, so a `view=` or `technician_id=` query arg can't widen what they see. Multi-entity aggregate queries whose first selected column belongs to the JOIN TARGET (e.g. `query(Facility.name, count(WorkOrder.id)).join(Facility, ...)`) must say `.select_from(WorkOrder)` explicitly or SQLAlchemy can't pick the join origin. Charts use the Chart.js 4 bundle already in static/js/plugins (data passed as one `window.MO_DASHBOARD` JSON blob from a CSP-nonce'd inline script; static/js/mo_dashboard.js draws every `<canvas data-chart>`). Reports & Exports (application/reports.py, routes `reports_index` at /reports and `view_report` at /reports/<key>): every one of the 13 reports named in the phase list reuses an existing module's already-defined metric — risk.calculate_risk() (Capital Replacement), vendors.compute_vendor_stats()/expiration_status() (Vendor Performance), costs.cost_rollup() (Maintenance Cost), analytics.facility_health_scores()/detect_recurring_issues() (Facility Condition, Recurring Problems) — this module is a thin, tabular, CSV-exportable view over them, never a second definition of a metric already defined elsewhere. Each `rows(filters)` builder returns `(headers, rows, truncated)` where every row is a list of PLAIN values (str/int/float/date/None via `_fmt()`) — the exact same values render in the HTML table and the CSV file, so there's exactly one source of truth per report; never build a separate "display version" with links/HTML in it. `filters` is a superset of analytics.py's filter-dict shape (adds `vendor_id`/`asset_id`/`dimension`) specifically so `report_facility_condition()`/`report_recurring_problems()` can hand it straight to `analytics.facility_health_scores()`/`detect_recurring_issues()` unchanged — analytics.py ignores the extra keys harmlessly via `.get()`. `parse_date`/`days_between`/`num`/`pct` in analytics.py are PUBLIC (renamed from Phase 9's `_parse_date`/`_days_between`/`_num`/`_pct` when reports.py needed to reuse them) — grep before reusing an analytics.py helper from another module; if it's still underscore-prefixed, promote it rather than reaching into the private name. **Gotcha hit while wiring the nav link**: `{% if current_path.startswith(...) %}` raised `UndefinedError` on every route that doesn't pass `current_path` into its template context (most "add_X"/"edit_X" routes only pass `current_page_name`) — Jinja's `Undefined` silently evaluates `==` comparisons to False (which is why every pre-existing `{% if current_path == '/x' %}` check in nav.html was always safe) but raises on any method call like `.startswith()`. Use `request.path` (always present) for any new prefix/method-based nav check, never the possibly-unpassed `current_path` context variable. Every report caps its result at `MAX_EXPORT_ROWS` (20,000) and flags `truncated` rather than silently dropping rows or loading an unbounded set, per the performance baseline; the on-screen table additionally slices to `DISPLAY_ROWS` (200) while the CSV export gets the full (capped) set — verified via `EXPLAIN QUERY PLAN` that every report's `work_order` queries use an index, 0 full scans.

Failed-item work-order generation (application/inspections.py): generate_work_order_for_failures(inspection, user) is called from inside record_inspection_results() in the SAME transaction that writes the InspectionResult rows and flips the inspection to Completed — it reads inspection.results (already-flushed-but-not-committed) to find Fail rows, so it must run after db.session.flush() but before db.session.commit(). It creates at most ONE combined work order per inspection (not one per failed item) — see the docstring for why. 'Needs Attention' never triggers generation, only 'Fail' does; the "generate a work order" checkbox on the results form is an opt-out, checked by default, not an opt-in.

SLA (application/sla.py, model SLARule, routes `sla_rules`/`edit_sla_rule`/`delete_sla_rule`): one admin-configured rule per Priority (unique `priority_id`); a priority with no row has no SLA tracking at all, never a fabricated deadline. Response/resolution due-at are computed on read (`created_at + rule.hours`), never stored on WorkOrder — a rule change applies to a work order's remaining lifetime. "Response met" reuses the SAME `started_at`-based proxy Phase 9's `avg_response_days` already uses (time to IN_PROGRESS) rather than adding a second, competing "responded to" timestamp — see docs/PHASE_11_REPORT.md for why a new column wasn't added. `analytics.work_order_kpis()`'s `sla_compliance` is now DUAL-MODE: it tries `sla._rule_based...` first (one cheap COUNT query if no active rule exists anywhere) and only falls back to the original due-date approximation when no configured rule covers any of the period's completions — this is backward-compatible by construction (every Phase 9/10 test that never creates an SLARule takes the untouched fallback path) but means **any test that creates a persistent, active SLARule for a given Priority changes the SLA numbers for every OTHER test file's completed work orders of that same priority**, since the check is global, not scoped to a facility/filter. Every `_ids()`-style test helper across this project defaults to priority='High' — tests/test_sla_and_notifications.py therefore uses 'Critical' for every SLARule it leaves active, specifically to avoid contaminating other files' 'High'-priority fixtures in the shared session-scoped test DB (found via a reordered-file run, `pytest tests/test_search_and_csv_import.py tests/test_sla_and_notifications.py tests/test_dashboard.py ...`, that only fails in that order — always run at least one reordering after adding a test that creates admin-configurable global state). `analytics.sla_summary()` (the dashboard breach/warning panel) has the same global-rule-existence short-circuit and the same "use an unclaimed priority in tests" rule applies to it too.

Notifications (application/notifications.py, models NotificationPreference/NotificationLog, scheduled job `run_notification_sweep` in scheduled_jobs.py registered 2am daily in main.py, one hour after PM generation): 8 categories from PROJECT_PLAN.md — pm_due/pm_overdue/inspection_due/inspection_failed/vendor_contract_expiring/asset_warranty_expiring/sla_warning/sla_breach. Two trigger shapes: everything except `inspection_failed` is SCAN-based (found fresh by the sweep every run); `inspection_failed` is EVENT-based, called once from `routes.record_inspection_results()` right after commit — it is never part of the sweep (`run_notification_sweep()`'s summary always reports 0 for it). De-duplication is the core mechanic: `NotificationLog` has a unique constraint on (event_type, entity_type, entity_id, bucket, user_id); `bucket_key()` maps a transient condition (due today) to a DAY string (reminds once) and a persistent one (overdue, expiring, breach) to an ISO-WEEK string (reminds on a cadence, not every single day) — `EVENT_CADENCE` in notifications.py is the one place this mapping lives. A user with no `NotificationPreference` row is treated as "everything on" (`preference_allows()`), so a brand-new account doesn't silently miss alerts. Recipients are Admin+Specialist (`staff_recipients()`) for every category, PLUS the assigned technician specifically for `sla_warning`/`sla_breach` on their own work order. **Bug caught while wiring `_notify_sla()`**: it originally called `sla.rules_by_priority()` (returns a `{priority_id: rule}` DICT) and then passed that dict straight into `sla.scan(candidates, rules, now)`, whose `rules` parameter expects a raw iterable of SLARule OBJECTS (it calls `rules_by_priority()` internally) — iterating the dict yielded priority-id ints, not rule objects, raising `AttributeError: 'int' object has no attribute 'priority_id'` on first real-data smoke test. Fixed by checking rule existence directly (`SLARule.query...first()`) and passing `rules=None` to `scan()`, letting it resolve rules itself. Lesson: never pre-resolve a helper's own internal `rules_by_priority()` call before passing the result back into a function whose signature still expects the raw form.

Global Search (application/search.py, route `search` at /search): one ILIKE query per entity type (work orders, facilities, rooms, assets, vendors, projects, users), each capped at `RESULTS_PER_TYPE`. Users are searchable by NAME ONLY — `User.email_enc`/`email_hash` are encrypted/hashed at rest (see the User model), so a partial ILIKE match against email is not possible, only an exact hash match is. The Users result group is also restricted to Admins (`include_users` param, resolved in the route via a non-aborting `is_admin_bool()` helper — `is_admin()` itself would abort(403) the whole page for non-admins, wrong here since search must stay usable for everyone).

Audit Log (application/audit.py, model AuditLog, route `audit_log` at /audit_log, admin-only, read-only): NOT written by routes. Two SQLAlchemy `Session` listeners registered once by `import application.audit` in main.create_app — `before_flush` records one 'update' row PER CHANGED COLUMN for every dirty instance whose class name is in `audit.TRACKED`, and a 'delete' row per deleted one; `after_flush` records 'create' rows (new objects have no id until after the flush). This means every path that saves a tracked model is audited — routes, the PM generator, the CSV importer, the notification sweep — with no per-call-site bookkeeping to forget. The acting user comes from flask_login's current_user when there's a request context, else NULL (rendered "System"). Two non-obvious things: (1) a column in `MASKED_FIELDS` (password, email_enc/email_hash, lockout state) is logged as changed with both values '***' — the equality short-circuit that drops no-op writes runs on the RAW values BEFORE masking, otherwise every password reset would be silently dropped as "old == new" (that exact bug shipped for one smoke-test run); (2) after a commit expires an instance, a second edit's attribute history has no `deleted` side — `_committed_value()` reads the pre-change value with a Core SELECT on the flush's own connection (Core, so no autoflush, so no recursion into the listener); `AttributeState.load_history()` does NOT do this for scalar columns despite its docstring. Add a model to `TRACKED` by class NAME string; anything not listed is silently un-audited. The listener fires in tests too, so every test that saves a tracked model also writes AuditLog rows — harmless, but don't assert exact AuditLog counts across a whole shared-session table, filter by entity_type/entity_id.

Security review (Phase 12, docs/PHASE_12_REPORT.md has the full checklist): every M&O route has `@login_required` plus a guard; sub-resource routes (labor/material/attachment/task/cost/document deletes) derive the parent from the ROW, never from a request param; every download route passes a DB-stored, `secure_filename()`-generated name to `send_from_directory` (a tampered `../` name 404s — tested); uploads go through `validate_file_upload()` (extension AND magic-byte check) then a generated filename; `CSRFProtect` is global (a token-less POST is 400 — tested, and a legacy template, organization.html, actually depends on CSRF being on: it reads `csrf_token._value()` inline, so it can't render under the test suite's CSRF-off config — test it with `app.config['WTF_CSRF_ENABLED'] = True` toggled in a try/finally, never by editing the legacy template). `/search` and the CSV upload got `@limiter.limit`. CSV Import (application/csv_import.py, model CsvImportLog, routes `csv_import_index`/`csv_import_upload`/`csv_import_template`): a SEPARATE, self-contained tool from the legacy `/bulk-data-upload` (Users+Sites, FTP-schedulable, kept as-is) — this one covers Facilities/Rooms/Assets/Vendors/Users with one uniform two-phase shape: `validate_rows()` is a pure, no-DB-writes pass producing a per-row 'valid'/'duplicate'/'error' report (a duplicate — natural key already exists, or repeats an earlier row in the file — and an error — missing/invalid field — are both non-fatal, just excluded from the commit); `commit_rows()` adds every valid row to ONE session and commits ONCE, rolling back the entire batch on any exception. This is the guarantee tested by `test_partial_failure_does_not_corrupt_prior_successful_import`: a failed batch can't retroactively corrupt an EARLIER, separately-committed successful import, because each upload's rows share one transaction distinct from any other upload's.

Test-writing gotchas discovered while adding tests/test_pm.py (both apply broadly, not just to PM):
- **Never issue an authenticated request with one identity/client and then a different identity's client in the same test function** — reproducibly (even on the pre-existing /sites route, nothing to do with PM) the second client's request resolves current_user as the FIRST client's identity, not its own. Every site-/ownership-scoping test in this project therefore takes only `app` (never a second client fixture), creates its setup data directly via the ORM, and makes HTTP requests as exactly one identity — see test_facilities.py's `test_room_site_scoping_for_other_site_user`, test_assets.py's `test_qr_respects_site_scoping`, or test_pm.py's `test_technician_sees_only_own_site_schedules` for the pattern. This has not been root-caused (Flask-Login/Werkzeug test client internals); treat it as a hard rule, not a suggestion.
- **Never assume a row's autoincrement id (or anything derived from it, like WorkOrder.wo_number) based on "this is the first one this test file creates."** Tests share one session-scoped database across every test module; a WorkOrder id that was reliably 1 before tests/test_pm.py existed stopped being 1 once test_pm.py (which sorts alphabetically earlier and creates its own work orders) was added. Look rows up by a distinguishing name/title instead, the way every other cross-entity test helper in this project already does.
