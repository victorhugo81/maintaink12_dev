### Access model

- **GET** list/detail: any logged-in user; Admin/Specialist (`role_id` 1/2) see all sites,
  everyone else only their own site (`can_access_site`). Non-admins get the detail page
  with fields `readonly`/`disabled` and management controls hidden.
- **POST** (create/edit/deactivate, floors, attachment upload/delete): `is_admin()` only,
  matching Site management. Enforced server-side — the disabled attributes are UX only.

## Deviations from the plan (and why)

1. **Field lists were chosen, not taken from the plan.** The prompt says "fields per
   PROJECT_PLAN.md section Data Model," but that section only names the models — it never
   enumerates Facility/Floor/Room fields. The fields above are a reasonable K-12 M&O set;
   easy to extend additively later.
2. **Soft delete on Facility/Room** deviates from every existing AssistItK12 model (all
   hard-delete). Required by the plan so later phases' work orders/assets/inspections keep
   history. Floor still hard-deletes, but is blocked while it has rooms — an application
   check rather than relying on the `ON DELETE SET NULL` FK, because SQLite (tests) doesn't
   enforce it the way MySQL (production) does.
3. **Floor has no standalone pages.** The prompt asks for CRUD only on Facilities and Rooms,
   so floors are add/delete-only, inline on the facility detail page.
4. **Floor carries no `site_id`.** The plan's "every relevant record carries a site
   relationship" list names Facility and Room, not Floor; Floor is always reached through
   its Facility, so it wasn't denormalized.
5. **Read access is broader than Site management.** AssistItK12 gates even the Sites *list*
   to Admins. For Facilities/Rooms, GET is open to all users (site-scoped) because the plan
   expects site-level staff to see their locations and later phases build on that (work
   orders "from here", QR landing pages). Mutation stays Admin-only — the plan's expanded
   role set (M&O Director, Supervisor, etc.) is not built yet, so no intermediate tier exists.
6. **Single-file attachment per submit**, not multi-photo/camera capture. The prompt asks
   for "basic" support reusing the existing mechanism, and the existing mechanism is
   single-file. Multi-upload is a later-phase concern per the plan's Photo & QR section.
7. **"Run migrations against a fresh DB" was satisfied differently than literally stated.**
   AssistItK12's migration chain cannot run from an empty database (its root revision
   assumes the baseline tables exist — pre-existing quirk, documented in
   `PHASE_0_ARCHITECTURE_ANALYSIS.md` §5). Fresh installs use `seed_data.py` →
   `db.create_all()`, which was verified to work and includes the new tables. The migration
   itself was verified against a simulated already-in-production baseline, which is the
   scenario that actually matters.
8. **One touch on an existing model**: `Site.facilities` backref added (no schema change).
9. **Not done, deliberately:** no Assets, no WorkOrder, no dashboard changes, no new roles,
   no QR codes — all later phases.
