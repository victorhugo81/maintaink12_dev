What This App Is
Maintaink12 is a lightweight CMMS / work-order management system for K-12 district Maintenance & Operations (M&O) departments, built directly on top of the AssistItK12 codebase (a K-12 IT ticketing platform: users, roles, sites, tickets, assignments, attachments, notifications, reporting). See docs/PROJECT_PLAN.md for the full target vision, data model, KPI list, and phased build-out — read it before extending this app. Maintaink12 and AssistItK12 are separate projects (no shared git history); this repo started as a copy of AssistItK12's application code and diverges from here via the phases in docs/MAINTAINK12_PLAN_AND_PROMPTS.md.

As of Phase 13, the AssistItK12 ticketing system (Ticket/Title/Ticket_content/Ticket_attachment, /tickets, /titles, and every route in between) has been removed entirely — see docs/PHASE_13_REPORT.md. It was a deliberate, documented parallel track through Phase 12 (see the superseded note on WorkOrder below), but once WorkOrder covered every case Ticket did, the user asked for it gone and for the M&O Dashboard to become the app's home page. The app now contains only the M&O modules built so far: Facility/Floor/Room (Phase 1), AssetType/Asset/AssetConditionHistory with QR codes (Phase 2), WorkOrder with Priority/Category/Subcategory and a status workflow (Phase 3), MaintenancePlan/MaintenanceSchedule with automatic PM work-order generation (Phase 4), InspectionTemplate/Inspection/InspectionResult with due/overdue tracking and failed-item work-order generation (Phase 5), Vendor with a WorkOrder.vendor_id link and a performance view (Phase 6), WorkOrderLabor/WorkOrderMaterial/CostRecord with cost rollups and technician workload (Phase 7), Project/ProjectTask/ProjectCost/ProjectDocument with Asset Risk Scoring and Capital Replacement (Phase 8), the role-based M&O Dashboard at /dashboard with Facility Health Scores, Recurring Issue Detection and Operational Insights (Phase 9 — no new models, one new index), thirteen CSV-exportable Reports at /reports (Phase 10 — no new models, no new migration, pure reuse of existing modules), and SLARule/NotificationPreference/NotificationLog/CsvImportLog powering configurable SLA targets + breach/warning tracking, an 8-category email notification sweep, global search, and a generalized CSV import tool for Facilities/Rooms/Assets/Vendors/Users (Phase 11), and an automatic field-level AuditLog plus the security/mobile review (Phase 12) — all in application/models.py, the "(M&O)" sections of routes.py, application/workflow.py, application/reference_data.py, application/pm.py, application/inspections.py, application/vendors.py, application/costs.py, application/risk.py, application/projects.py, application/analytics.py, application/reports.py, application/sla.py, application/notifications.py, application/search.py, application/csv_import.py, and the templates (now rendered at "/", not "/dashboard" — see the Phase 13 note in the M&O Dashboard section below). WorkOrder was originally built as a separate model from Ticket, not an extension of it (docs/PHASE_0_ARCHITECTURE_ANALYSIS.md, Recommendation 2) — that decision is exactly what made Phase 13's full removal of Ticket possible without touching WorkOrder at all. PROJECT_PLAN.md's original Phase 6 scope also included Inventory tracking (InventoryItem/InventoryTransaction) — the user explicitly cut that from the plan before Phase 6 was built, so it was never implemented; see docs/MAINTAINK12_PLAN_AND_PROMPTS.md's Phase 6/7/11 sections, which were all updated to remove the dependency (Phase 7's own CostRecord material cost comes from WorkOrderMaterial, never from inventory). As of Phase 14, InspectionCycle/InspectionAttachment (both additive — InspectionCycle is new, Inspection.cycle_id is a nullable FK, InspectionAttachment mirrors Facility/Room/Asset's attachment pattern) power the "Facilities Audit" workflow (user-renamed from "Summer Walkthrough" — the routes/endpoints/URLs still literally say walkthrough, e.g. /start_walkthrough, /walkthrough/<id>, StartWalkthroughForm; only user-facing labels changed): application/inspections.py's start_walkthrough()/next_incomplete_room_inspection()/inspection_progress() bulk-create one Inspection per room for a cycle+template, step through them via a fast mobile UI at /walkthrough/<id> (big Good/Issue/Critical/N/A buttons mapped onto the existing Pass/Needs Attention/Fail/N/A InspectionResult values — no new triage model), and roll up completion % at the facility and district level; the M&O Dashboard and the Facilities page both show this rollup (a completion gauge, per-school KPI tiles and progress bars) — see docs/PHASE_14_REPORT.md. `/start_walkthrough`'s Cycle and Checklist Template selects come first in the form, above Site/Building, because Site/Building are filtered by whichever (cycle, template) pair is currently picked: `application/inspections.py`'s `pending_facility_ids(cycle_id, template_id, facility_ids)` is template-scoped (unlike `inspection_progress()`, which is cycle-only and feeds the dashboard/facilities rollups instead) — a facility 100%-complete under one template can still have every room pending under another. There's no explicit template-to-facility scoping in the data model (nothing stops picking "Playground Safety" at a building with no playground), so the route also intersects with `facilities_ever_inspected_under_template(template_id, facility_ids)` — a building only qualifies once this exact template has actually been used there before, via a prior walkthrough or an ad hoc `/add_inspection`; a template nobody's used anywhere yet shows zero eligible buildings and a message pointing at Schedule Inspection to assign it first (`#no-eligible-buildings` in the template, which also disables the submit button via JS). The route precomputes a `pending_matrix` dict keyed `"{cycle_id}_{template_id}"` across every existing cycle x template combo and passes it to the template; `form.site_id.choices`/`form.facility_id.choices` are the full unfiltered lists, and the page's own JS hides/disables options live as Cycle/Template/Site change, auto-correcting the selection to the first still-visible option (same pattern Phase 14 introduced for Site -> Building). This relies on exactly one InspectionCycle ever being `is_active`, enforced in `add_inspection_cycle`/`edit_inspection_cycle` (deactivates every other cycle when one is saved active), not a DB constraint — though `is_active` itself no longer gates this dropdown filtering, since `pending_matrix` covers every cycle, not just the active one. `N/A` was added as a fourth InspectionResult value (a checklist item that doesn't apply to this room) — it's excluded from both `inspection_progress()`'s `issues_open` count and `facility_health_scores()`'s inspection-failure-rate denominator, never treated as a pass or a fail. `/site_details/<site_id>` is a read-only school-level dashboard (site info, a completion gauge, Open/Pending/Closed work-order status cards, the Facility Health Score table) — a level above edit_facility.html, scoped the same way via can_access_site(). This extends the existing Inspection/WorkOrder system rather than building a second one, the same lesson Phase 13's Ticket removal taught this codebase about parallel systems. `/add_inspection` ("Schedule Inspection") is deliberately kept separate from `/start_walkthrough` ("Facilities Audit") — the latter always bulk-schedules every active room in a facility under a cycle; the former is for ad hoc scheduling outside the cycle workflow, and its `InspectionForm.room_ids` (a `SelectMultipleField` rendered as a checkbox list, filterable by Site/Facility/text search in the template's JS) lets a user bulk-schedule a *specific* subset of rooms in one submission — one `Inspection` row per room checked, same template/due_date/inspector/notes on each. If any room is checked, `room_ids` wins outright over `facility_id` (which doubles as a room-list filter, not just a standalone target) — `facility_id`/`asset_id` only go through the old one-target-only `_validate_inspection_target()` path when no rooms are checked. Both targets still respect `ck_inspection_single_target` (exactly one of facility_id/room_id/asset_id set per row) — the bulk path always sets `facility_id=None` on each created row, never the room's own facility. Everything below describes the AssistItK12 foundation this was built on, except where a section explicitly calls out the M&O additions. Per-phase deliverables live in docs/PHASE_*_REPORT.md.

Running the App
# Run dev server
uv run flask --app main.py run

# Or activate the venv and use flask directly
source .venv/bin/activate
flask --app main.py run
Dependencies are managed with uv. To add or sync packages:

uv sync
uv add <package>
Database
MySQL via PyMySQL in production; SQLite (DATABASE_URL=sqlite:///...) works fine for local dev — set FLASK_CONFIG=development in .env either way. Connection string is in .env as DATABASE_URL.

# Apply all pending migrations
flask --app main.py db upgrade

# Generate a new migration after model changes
flask --app main.py db migrate -m "description"

# Check current migration version
flask --app main.py db current
Migration files live in migrations/versions/. After adding or changing a model, always run migrate then upgrade. IMPORTANT: the migration chain's root revision (b47d77fd2576) is not runnable against a truly empty database — it assumes the baseline AssistItK12 tables already exist (created via db.create_all(), the way installation/seed_data.py bootstraps a fresh install). To test a migration against a "pre-existing production" baseline instead, create all tables except the ones your migration adds (db.metadata.create_all(bind=db.engine, tables=[...])), `flask db stamp <previous head>`, then `flask db migrate` / `db upgrade` — that's how the Facility/Floor/Room migration (7d40fabd6b8b) was verified additive.

Adding a column to an EXISTING table (not just creating new tables) needs a stricter baseline than the "skip the new tables" trick above — that trick only works when nothing about existing tables changes. Phase 6's `WorkOrder.vendor_id` needed the real work_order table minus exactly that one column; the reliable way to build that is to compile the table's real CREATE TABLE DDL (`str(CreateTable(table).compile(engine))`), strip just the target column's line (regex-fix the resulting trailing comma), execute that DDL directly, then `create_all()` every other table normally. Naively rebuilding the table from `Column.copy()`-filtered columns loses constraint fidelity (names, etc.) and produces false "everything changed" autogenerate diffs — a case of the surgery itself, not the real migration, being broken. Don't trust a `Column.copy()`-based baseline for this class of change.

flask-migrate's `render_as_batch` default means autogenerate ALWAYS wraps an ALTER in `op.batch_alter_table(...)`, on every backend, not just SQLite. That's normally harmless — MySQL executes the enclosed operations as plain ALTERs when it can. But adding a NEW FOREIGN KEY CONSTRAINT to an EXISTING SQLite table forces batch mode into its "recreate the whole table" strategy, which requires every one of the table's pre-existing constraints to be reflectable with a name — and none of this project's FKs have explicit names (plain `db.ForeignKey(...)` on a Column, no `name=`). That combination fails with `ValueError: Constraint must have a name` on SQLite; MySQL has no such limitation (a plain `ADD COLUMN ... ADD CONSTRAINT` needs no recreate there). The Phase 6 migration (`a370d33e0db2`) works around this by checking `op.get_bind().dialect.name` and only adding the DB-level FK constraint on non-SQLite backends — SQLite gets the column and the ORM-level relationship, just not a database-enforced constraint on that one column. Keep this pattern in mind for any future migration that adds a FK-referencing column to a table that already has other unnamed FKs on it.

Seeding Data
# 1. Create MySQL DB and write .env (interactive)
python installation/create_env.py

# 2. Seed roles, default site, admin user (interactive)
python installation/seed_data.py
seed_data.py calls db.create_all() itself, so it's also the fresh-install path for local SQLite dev — no need to run `flask db upgrade` first. Note: the admin email you enter is validated with WTForms' Email() (via the email-validator package), which rejects RFC 2606 reserved domains/TLDs (example.com, .test, .invalid, .local, etc.) with no visible form error on login.html — use an ordinary-looking domain for seeded/test accounts. Re-running the script against an existing DB with the SAME admin email crashes on a UNIQUE constraint (user.email_hash) — a pre-existing bug: `User.query.filter_by(email=admin_email)` doesn't match because `email` is encrypted at rest (looked up via a separate `email_hash` column instead), so the "user already exists, update it" branch never triggers. Not touched as part of the Phase 14 inspection-template seeding work below; flagged here since it blocks a clean idempotent re-run of the whole script (the Organization/Role/Site blocks above it, and the Reference-data/Inspection-template blocks below it, are all independently idempotent and unaffected). seed_data.py also seeds the same 6 starter InspectionTemplates (Annual Facility Audit, Playgrounds & Outdoor Facilities, Safety & Equipment, Office Spaces, Classrooms, HVAC Systems) and their checklist items that ship in the dev DB — each template's items are a themed subset of `reference_data.DEFAULT_INSPECTION_QUESTION_PRESETS` (inlined again in seed_data.py itself, same reasoning as the migration: a seed/install script's data shouldn't silently drift if the reference-data defaults change later), idempotent by template name then by question-within-template.

Architecture
App Factory
main.py contains create_app(config_name). It initializes Flask extensions (SQLAlchemy, Flask-Login, CSRF, Flask-Mail, Flask-Limiter, APScheduler), registers the single blueprint, applies security headers, and wires database-stored SMTP config from the Organization model. It also creates the upload folders: UPLOAD_FACILITY_ATTACHMENT, UPLOAD_ROOM_ATTACHMENT, UPLOAD_ASSET_ATTACHMENT, and UPLOAD_WORK_ORDER_ATTACHMENT (the legacy UPLOAD_ATTACHMENT folder for ticket attachments was removed in Phase 13).

All routes live in application/routes.py under one blueprint (routes_blueprint), organized into labeled sections:

Users / Roles / Sites / Notifications / Organization — admin management
Facilities / Rooms (M&O) — see below

Facilities / Rooms (M&O) access model
GET (list/detail) is open to any @login_required user, scoped by can_access_site() in routes.py — Admins/Specialists (role_id 1/2) see every site, everyone else only their own. POST (create/edit/delete/floor management/attachment upload+delete) is gated by is_admin(), matching how Site management already works — there's no partial "M&O role" permission model yet, since PROJECT_PLAN.md's expanded role list (M&O Director, Supervisor, Technician, etc.) hasn't been built. edit_facility.html/edit_room.html/edit_asset.html render the same page for both cases, just with form fields marked readonly/disabled and the management controls hidden for non-admins — the real enforcement is server-side in the POST handlers, not the disabled attribute. One exception: add_asset_condition (recording a condition assessment) is open to role_id 1-3 (Admin/Specialist/Technician), site-scoped, because technicians are the ones inspecting equipment. AssetType CRUD (list included) is admin-only like Sites.

Work order access (can_access_work_order / can_manage_work_order in routes.py): Admin/Specialist (1/2) see and manage everything; Technicians (3) see and manage their own site's; everyone else sees only work orders they requested or are assigned to, and may comment but not edit or change status. "Staff" (is_staff(), roles 1-3) can create Manual work orders via /add_work_order; anyone can submit a Request via /request_work_order, limited to facilities at their own site. Assigning a technician to a New work order auto-moves it to Assigned (the only place a status changes outside the status-change route, and it still goes through apply_transition). /request_work_order and /add_work_order are two routes sharing one template (new_work_order.html) with Bootstrap tabs — "Request Maintenance" (WorkOrderRequestForm, open to everyone, default-active tab) and "Full Work Order" (WorkOrderForm, same fields as edit_work_order.html, rendered only when `full_form` is non-None i.e. role_id 1-3). `_work_order_create_context(current_page_name)` builds both forms' choices/location maps in one place so both routes (including each one's validation-failure re-render) stay consistent; `/add_work_order` opens with the Full tab active, `/request_work_order` with Request active, via the `active_tab` kwarg. Each tab is its own `<form action=...>` posting to its own route (same multi-form-one-page pattern as organization.html's General Settings/Email Config/Test Email sections) — there's no single shared submit.

Detail pages with a secondary action (add floor, record condition, change status, add comment, add subcategory) put that secondary <form> OUTSIDE the main edit <form> — HTML doesn't allow nested forms, and a browser silently folds the inner form's fields into the outer one, so the secondary submit button posts the wrong form. This bit edit_facility.html once; curl-based smoke tests don't catch it, a nested-form depth check on rendered HTML does.

QR codes: /asset_qr/<id>.png renders on the fly with the `qrcode` library (no stored image) and encodes asset_qr_url(asset) = the edit_asset detail URL built with _external=True — so it depends on the request host/scheme (behind a proxy, ProxyFix in main.py is what makes that right). Login is still required to open the page a QR resolves to.

Key Conventions
Soft delete for M&O structural data: Facility.is_active / Room.is_active, not a DB row delete — see the Models table above. Existing AssistItK12 entities (Site, Role, Notification) still hard-delete.
WTForms BooleanField + hidden checkboxes: a checkbox field only appears in POST data when checked — omitting it (e.g. in a test, or a customized form) silently sets the field False. FacilityForm.is_active / RoomForm.is_active rely on this being resent correctly by the real template; add_facility.html/add_room.html never render the field at all, so new records keep the column default (Active) instead of risking this footgun.

Site → Building cascading dropdowns (new_work_order.html, start_walkthrough.html): the route builds a `facility_sites` dict (`{facility_id: site_id}`) alongside the normal WTForms `choices` list and passes it to the template; a small nonce'd script (`{{ facility_sites|tojson }}`) hides/disables Building `<option>`s that don't match the selected Site, with no page reload, falling back to the first matching option since Building is required. Server-side, `facility_sites.get(form.facility_id.data) != form.site_id.data` catches a mismatched submission even with JS disabled or stale. Backend Security Architecture
These patterns came out of a full security audit and its fixes — preserve them when touching nearby code.

Config resolution: create_app(config_name=None) in main.py resolves config_name from the FLASK_CONFIG env var, falling back to 'default', which maps to ProductionConfig in config.py. Local development must set FLASK_CONFIG=development in .env (DevelopmentConfig is the only place SESSION_COOKIE_SECURE is turned off, for plain-HTTP testing). The production startup guards in create_app compare the resolved class (config[config_name] is ProductionConfig), not the string 'production' — so they still fire when config_name resolves to 'default'. Don't reintroduce a string comparison there.

Facility/Room authorization: can_access_site(site_id) in application/routes.py is the read-access check for the M&O module's site-scoped detail/download routes (edit_facility, edit_room, download_facility_attachment, download_room_attachment) — Admins/Specialists (1/2) see any site, everyone else only their own. It only guards GET; every mutating Facility/Room route also calls is_admin() explicitly. Any new site-scoped detail-style route should call this helper (or the equivalent can_access_work_order/can_manage_work_order/can_access_inspection) rather than re-deriving its own role_id check — a route with its own slightly-different inline check is exactly how a Technician once could have reached another site's record by guessing an id in the URL, the failure mode this pattern exists to prevent (see docs/PHASE_12_REPORT.md's IDOR review, which audited every one of these checks).

edit_user authorization: non-admin "tech role" staff (Specialist/Technician) may only edit non-admin users at their own site. role_id and site_id choices are restricted server-side, not just in the rendered <select> — see the re-validation inside form.validate_on_submit(). Don't loosen this without equivalent re-validation; the original version let any tech-role account promote itself (or anyone) to Admin and reset any user's password.

delete_user blocks deleting your own currently-logged-in account and deleting the last remaining Admin (role_id=1).

Login (routes.py:login) always runs a password-hash comparison — even for a nonexistent account, via the module-level _DUMMY_PASSWORD_HASH — and always shows one generic failure message regardless of whether the account doesn't exist, has the wrong password, is inactive, or is locked. This is intentional (anti-enumeration); don't reintroduce per-case messages.

The real `db`/`login_manager`/etc. extension instances live in main.py and are what every module imports (`from main import db, login_manager, ...`) — application/__init__.py is now an empty file. It used to also construct its own separate `db = SQLAlchemy()` / `login_manager = LoginManager()` with `login_manager.login_message = ''` set on it, but nothing ever imported that module's objects, so the setting silently did nothing: Flask-Login's real (main.py) instance kept its library-default "Please log in to access this page." message regardless. Removed the dead duplicate rather than leave a second, never-wired-up set of extension objects sitting there as a trap for the next person who edits "the" login_manager and wonders why it has no effect — login_manager.login_message = '' now lives in main.py's create_app(), next to login_view.

CSP: main.py issues a fresh nonce per request (g.csp_nonce) and script-src only allows 'self' plus that nonce — there is no 'unsafe-inline' for scripts. Any new inline <script> block in a template must add nonce="{{ g.csp_nonce }}" or the browser will silently block it. **This also blocks every inline event-handler ATTRIBUTE** (onchange="...", onclick="...") in any CSP-enforcing browser, not just inline `<script>` tags — a nonce can only be attached to a `<script>` element, never to an onX= attribute, so `script-src 'self' 'nonce-x'` with no 'unsafe-inline' silently kills ALL of them regardless of nonce. This bit the whole app for an unknown amount of time: every `onchange="this.form.submit()"` filter/per-page dropdown across ~14 templates never actually auto-submitted in a real browser (pytest never caught it — tests hit routes directly via URL args, never exercising the onchange handler). Fixed by replacing the attribute with a `data-autosubmit` marker and a single delegated listener in includes/footer.html (`document.querySelectorAll('[data-autosubmit]').forEach(el => el.addEventListener('change', () => el.form.submit()))`) — use this pattern for any new auto-submitting select instead of an onchange attribute. A handful of one-off onclick/onchange handlers calling a named JS function (togglePwd, updateStatusLabel, saveFtpSettings, the FTP schedule checkbox toggle) were fixed the same way: give the element an id, remove the attribute, call `.addEventListener(...)` inside that page's own nonce'd `<script>` block instead. Verified with a real headless-Chromium (Playwright) pass, not just pytest — the Run skill's `examples/playwright.md` pattern (inject a signed Flask session cookie via `app.session_interface.get_signing_serializer(app).dumps(...)` to skip the login form, since there's no seeded password to log in with).

Named `name="submit"` form fields shadow `HTMLFormElement.submit`: any WTForms form with a plain `submit = SubmitField(...)` renders a button/input with `name="submit" id="submit"`, and HTML's named-form-element-as-property behavior means `document.getElementById(formId).submit` then resolves to *that button element*, not the native method — calling it throws `submit is not a function`. Hit this in walkthrough_room.html's and edit_inspection.html's "Mark Complete" JS shortcuts (both use `InspectionResultsForm`, which has exactly this `submit` field). Fix: call `.requestSubmit()` instead — it isn't a named property, so it's never shadowed. Only an issue for JS that programmatically submits a form containing a WTForms SubmitField; forms submitted by a normal user click never hit this.

Rate limiting: the Limiter in main.py has global default_limits (200/hour, 50/minute per IP), with the static endpoint explicitly exempted via a request_filter (otherwise normal page loads 429 on their own CSS/JS). Login (5/min), set_password and test_email (10/min), and add_comment (20/min) carry their own tighter @limiter.limit(...).

Dependencies: pip-audit is a dev dependency (uv run pip-audit) — run it before any release. It has already caught real, then-current CVEs in cryptography and idna once.

Preventive maintenance generation (application/pm.py): generate_due_work_orders(today=None, user=None) is the one place PM work orders get created — called by the daily APScheduler job (scheduled_jobs.run_pm_schedule_generation, registered unconditionally in main.py's create_app, 1am cron) AND directly by the admin "Run PM Generation Now" button (routes.run_pm_generation) AND by tests. Never duplicate this logic elsewhere. Duplicate-prevention works by advancing MaintenanceSchedule.next_due_date past `today` in the SAME transaction that creates the work order — there is no separate "already ran today" flag, the advanced date IS the guard. An overdue schedule (job didn't run for a while) still gets exactly ONE work order per call, with next_due_date fast-forwarded cycle-by-cycle past today — it does not backfill one work order per missed cycle. Schedules for a type-based plan are created lazily (_ensure_schedules), one per matching active asset, the first time generation runs after the plan/asset combination exists — so adding a new asset of a monitored type, or activating a new plan, doesn't need any migration or manual step to pick it up.

M&O Dashboard (application/analytics.py, route `index` at "/" as of Phase 13 — it lived at `mo_dashboard`/"/dashboard" through Phase 12, alongside the now-removed ticket dashboard that used to own "/"; `/dashboard` is kept as a thin redirect to "/" for old bookmarks, still served by the `mo_dashboard` endpoint): the ONE place PROJECT_PLAN.md's Canonical KPIs are computed; Phase 10's reports should call these functions, not re-derive KPIs. Reports & Exports (application/reports.py, routes `reports_index` at /reports and `view_report` at /reports/<key>): every one of the 13 reports named in the phase list reuses an existing module's already-defined metric — risk.calculate_risk() (Capital Replacement), vendors.compute_vendor_stats()/expiration_status() (Vendor Performance), costs.cost_rollup() (Maintenance Cost), analytics.facility_health_scores()/detect_recurring_issues() (Facility Condition, Recurring Problems) — this module is a thin, tabular, CSV-exportable view over them, never a second definition of a metric already defined elsewhere. Each `rows(filters)` builder returns `(headers, rows, truncated)` where every row is a list of PLAIN values (str/int/float/date/None via `_fmt()`) — the exact same values render in the HTML table and the CSV file, so there's exactly one source of truth per report; never build a separate "display version" with links/HTML in it. `filters` is a superset of analytics.py's filter-dict shape (adds `vendor_id`/`asset_id`/`dimension`) specifically so `report_facility_condition()`/`report_recurring_problems()` can hand it straight to `analytics.facility_health_scores()`/`detect_recurring_issues()` unchanged — analytics.py ignores the extra keys harmlessly via `.get()`. `parse_date`/`days_between`/`num`/`pct` in analytics.py are PUBLIC (renamed from Phase 9's `_parse_date`/`_days_between`/`_num`/`_pct` when reports.py needed to reuse them) — grep before reusing an analytics.py helper from another module; if it's still underscore-prefixed, promote it rather than reaching into the private name. **Gotcha hit while wiring the nav link**: `{% if current_path.startswith(...) %}` raised `UndefinedError` on every route that doesn't pass `current_path` into its template context (most "add_X"/"edit_X" routes only pass `current_page_name`) — Jinja's `Undefined` silently evaluates `==` comparisons to False (which is why every pre-existing `{% if current_path == '/x' %}` check in nav.html was always safe) but raises on any method call like `.startswith()`. Use `request.path` (always present) for any new prefix/method-based nav check, never the possibly-unpassed `current_path` context variable. Every report caps its result at `MAX_EXPORT_ROWS` (20,000) and flags `truncated` rather than silently dropping rows or loading an unbounded set, per the performance baseline; the on-screen table additionally slices to `DISPLAY_ROWS` (200) while the CSV export gets the full (capped) set — verified via `EXPLAIN QUERY PLAN` that every report's `work_order` queries use an index, 0 full scans.

Failed-item work-order generation (application/inspections.py): generate_work_order_for_failures(inspection, user) is called from inside record_inspection_results() in the SAME transaction that writes the InspectionResult rows and flips the inspection to Completed — it reads inspection.results (already-flushed-but-not-committed) to find Fail rows, so it must run after db.session.flush() but before db.session.commit(). It creates at most ONE combined work order per inspection (not one per failed item) — see the docstring for why. 'Needs Attention' never triggers generation, only 'Fail' does; the "generate a work order" checkbox on the results form is an opt-out, checked by default, not an opt-in.

SLA (application/sla.py, model SLARule, routes `sla_rules`/`edit_sla_rule`/`delete_sla_rule`): one admin-configured rule per Priority (unique `priority_id`); a priority with no row has no SLA tracking at all, never a fabricated deadline. Response/resolution due-at are computed on read (`created_at + rule.hours`), never stored on WorkOrder — a rule change applies to a work order's remaining lifetime. "Response met" reuses the SAME `started_at`-based proxy Phase 9's `avg_response_days` already uses (time to IN_PROGRESS) rather than adding a second, competing "responded to" timestamp — see docs/PHASE_11_REPORT.md for why a new column wasn't added. `analytics.work_order_kpis()`'s `sla_compliance` is now DUAL-MODE: it tries `sla._rule_based...` first (one cheap COUNT query if no active rule exists anywhere) and only falls back to the original due-date approximation when no configured rule covers any of the period's completions — this is backward-compatible by construction (every Phase 9/10 test that never creates an SLARule takes the untouched fallback path) but means **any test that creates a persistent, active SLARule for a given Priority changes the SLA numbers for every OTHER test file's completed work orders of that same priority**, since the check is global, not scoped to a facility/filter. Notifications (application/notifications.py, models NotificationPreference/NotificationLog, scheduled job `run_notification_sweep` in scheduled_jobs.py registered 2am daily in main.py, one hour after PM generation): 8 categories from PROJECT_PLAN.md — pm_due/pm_overdue/inspection_due/inspection_failed/vendor_contract_expiring/asset_warranty_expiring/sla_warning/sla_breach. Two trigger shapes: everything except `inspection_failed` is SCAN-based (found fresh by the sweep every run); `inspection_failed` is EVENT-based, called once from `routes.record_inspection_results()` right after commit — it is never part of the sweep (`run_notification_sweep()`'s summary always reports 0 for it). De-duplication is the core mechanic: `NotificationLog` has a unique constraint on (event_type, entity_type, entity_id, bucket, user_id); `bucket_key()` maps a transient condition (due today) to a DAY string (reminds once) and a persistent one (overdue, expiring, breach) to an ISO-WEEK string (reminds on a cadence, not every single day) — `EVENT_CADENCE` in notifications.py is the one place this mapping lives. A user with no `NotificationPreference` row is treated as "everything on" (`preference_allows()`), so a brand-new account doesn't silently miss alerts. Fixed by checking rule existence directly (`SLARule.query...first()`) and passing `rules=None` to `scan()`, letting it resolve rules itself. Lesson: never pre-resolve a helper's own internal `rules_by_priority()` call before passing the result back into a function whose signature still expects the raw form.

Global Search (application/search.py, route `search` at /search): one ILIKE query per entity type (work orders, facilities, rooms, assets, vendors, projects, users), each capped at `RESULTS_PER_TYPE`. Audit Log (application/audit.py, model AuditLog, route `audit_log` at /audit_log, admin-only, read-only): NOT written by routes. Two SQLAlchemy `Session` listeners registered once by `import application.audit` in main.create_app — `before_flush` records one 'update' row PER CHANGED COLUMN for every dirty instance whose class name is in `audit.TRACKED`, and a 'delete' row per deleted one; `after_flush` records 'create' rows (new objects have no id until after the flush). This means every path that saves a tracked model is audited — routes, the PM generator, the CSV importer, the notification sweep — with no per-call-site bookkeeping to forget. The acting user comes from flask_login's current_user when there's a request context, else NULL (rendered "System"). Two non-obvious things: (1) a column in `MASKED_FIELDS` (password, email_enc/email_hash, lockout state) is logged as changed with both values '***' — the equality short-circuit that drops no-op writes runs on the RAW values BEFORE masking, otherwise every password reset would be silently dropped as "old == new" (that exact bug shipped for one smoke-test run); (2) after a commit expires an instance, a second edit's attribute history has no `deleted` side — `_committed_value()` reads the pre-change value with a Core SELECT on the flush's own connection (Core, so no autoflush, so no recursion into the listener); `AttributeState.load_history()` does NOT do this for scalar columns despite its docstring. Add a model to `TRACKED` by class NAME string; anything not listed is silently un-audited. The listener fires in tests too, so every test that saves a tracked model also writes AuditLog rows — harmless, but don't assert exact AuditLog counts across a whole shared-session table, filter by entity_type/entity_id.

Security review (Phase 12, docs/PHASE_12_REPORT.md has the full checklist): every M&O route has `@login_required` plus a guard; sub-resource routes (labor/material/attachment/task/cost/document deletes) derive the parent from the ROW, never from a request param; every download route passes a DB-stored, `secure_filename()`-generated name to `send_from_directory` (a tampered `../` name 404s — tested); uploads go through `validate_file_upload()` (extension AND magic-byte check) then a generated filename; `CSRFProtect` is global (a token-less POST is 400 — tested, and a legacy template, organization.html, actually depends on CSRF being on: it reads `csrf_token._value()` inline, so it can't render under the test suite's CSRF-off config — test it with `app.config['WTF_CSRF_ENABLED'] = True` toggled in a try/finally, never by editing the legacy template). `/search` and the CSV upload got `@limiter.limit`. CSV Import (application/csv_import.py, model CsvImportLog, routes `csv_import_index`/`csv_import_upload`/`csv_import_template`): a SEPARATE, self-contained tool from the legacy `/bulk-data-upload` (Users+Sites, FTP-schedulable, kept as-is) — this one covers Facilities/Rooms/Assets/Vendors/Users with one uniform two-phase shape: `validate_rows()` is a pure, no-DB-writes pass producing a per-row 'valid'/'duplicate'/'error' report (a duplicate — natural key already exists, or repeats an earlier row in the file — and an error — missing/invalid field — are both non-fatal, just excluded from the commit); `commit_rows()` adds every valid row to ONE session and commits ONCE, rolling back the entire batch on any exception. This is the guarantee tested by `test_partial_failure_does_not_corrupt_prior_successful_import`: a failed batch can't retroactively corrupt an EARLIER, separately-committed successful import, because each upload's rows share one transaction distinct from any other upload's.

Test-writing gotchas discovered while adding tests/test_pm.py (both apply broadly, not just to PM):
- **Never issue an authenticated request with one identity/client and then a different identity's client in the same test function** — reproducibly (even on the pre-existing /sites route, nothing to do with PM) the second client's request resolves current_user as the FIRST client's identity, not its own. Every site-/ownership-scoping test in this project therefore takes only `app` (never a second client fixture), creates its setup data directly via the ORM, and makes HTTP requests as exactly one identity — see test_facilities.py's `test_room_site_scoping_for_other_site_user`, test_assets.py's `test_qr_respects_site_scoping`, or test_pm.py's `test_technician_sees_only_own_site_schedules` for the pattern. This has not been root-caused (Flask-Login/Werkzeug test client internals); treat it as a hard rule, not a suggestion.
- **Never assume a row's autoincrement id (or anything derived from it, like WorkOrder.wo_number) based on "this is the first one this test file creates."** Tests share one session-scoped database across every test module; a WorkOrder id that was reliably 1 before tests/test_pm.py existed stopped being 1 once test_pm.py (which sorts alphabetically earlier and creates its own work orders) was added. Look rows up by a distinguishing name/title instead, the way every other cross-entity test helper in this project already does.
